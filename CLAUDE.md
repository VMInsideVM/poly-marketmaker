# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A local single-user Flask web app that automates reward-farming market making on Polymarket. The end user is non-technical: they double-click an executable, a browser opens, they enter wallet private keys, and the app places/monitors orders to earn liquidity rewards. UI strings and user-facing messages are in 简体中文 — keep them that way. Intended to be packaged as a single exe via PyInstaller.

## Commands

```powershell
pip install -r requirements.txt   # also need pytest for the test suite
python app.py                     # run app; opens browser at http://127.0.0.1:5000 (/setup on first run)
pytest                            # run unit tests
pytest tests/test_strategy.py     # single file
pytest tests/test_strategy.py::TestMaxSpread2_TickSize1Cent::test_bid1_gt_2000_place_at_bid2  # single test
```

`tests/` holds pytest unit tests (pure logic, no network). The top-level `test_live.py`, `test_simulate.py`, `test_real_order.py` are **not** pytest tests — they are manual scripts that hit the real Polymarket API and the local `market_maker.db`; `test_real_order.py` places actual orders. Do not run them as part of a test suite.

## Architecture

**Auth gates everything.** Wallet private keys are AES-256-GCM encrypted with a key derived (PBKDF2, 600k iterations) from the user's password (`utils/crypto.py`). The key exists only in memory after login, so engines **cannot auto-start on boot** — the user must log in first. Note `app.py` imports but never calls `init_manager`; the `EngineManager` is constructed inside the `/setup` and `/login` routes (`web/routes.py`) once the encryption key is available. `web/routes.py` holds module-global `db`, `manager`, `encryption_key` — this is a deliberately single-process, single-user design.

**Threading model (`engine/manager.py`).** One shared `MarketScanner` thread produces an eligible-markets list using a single wallet's API (scanning needs no wallet-specific auth). Each enabled wallet gets a `WalletWorker` with its own thread that (a) places orders from the shared list and (b) monitors fills/stop-loss. The SQLite connection is opened once with `check_same_thread=False` and shared across all threads (`models/database.py`).

**Two operating modes** exposed via `/api/engine/*`:
- *Auto*: `start_all()` runs recovery + wallet workers + a periodic scanner loop.
- *Manual*: separate `scan` / `place-orders` / `start-monitors` endpoints so the user drives each step. Manual scan results are persisted to the `eligible_markets` table and surfaced live via `/api/eligible` (memory while scanning, DB when idle).

**Pipeline: scan → strategy → place → monitor.**
- `engine/scanner.py` filters reward markets (reward ≥ threshold, settlement days, price band, spread, cooldown) and computes an order price via `engine/strategy.py`. It does **not** filter by balance (the eligible list is shared across wallets with different balances); instead it records a per-market `min_cost = rewards_min_size × ceil_to_tick(reward_range_min)` (the minimum capital to place a reward-qualifying order) that each wallet gates on at placement time.
- `engine/strategy.py` (`determine_order_price`) is pure, fully unit-tested, and the core IP. It picks a buy price from orderbook bid depth using three different rules depending on tick size and `rewards_max_spread`. Change behavior here only with corresponding test updates.
- `engine/monitor.py` is API-driven, run as one tick (`WalletWorker._tick`). Step 1 (`check_buy_orders`) detects fills via CLOB `get_trades` (flattens `maker_orders` by funder, deduplicates by `(trade_id, order_id)` against a per-monitor trade-history watermark), records the buy for history, sets cooldown, and cancels the filled buy's remaining quantity — it no longer places the sell. Step 1b (`check_exit`) is **position-driven**: it maintains **exactly one** resting SELL per position; the cost basis is **reconstructed** from our real CLOB `get_trades` fills (`position_cost_with_lots` in `engine/take_profit.py`, via the monitor's per-tick `_cost_lots`). **`_cost_lots` must fetch with `get_trades(TradeParams(market=condition_id))`, NEVER `asset_id=`:** Polymarket's `/trades` server-side `asset_id` filter is broken — it returns an empty list even when fills for that exact `asset_id` exist (the account's other query forms return them), which silently left every position 裸奔 because the cost could never be reconstructed (real incident 2026-05-29). Filtering by `market` (condition_id) works, returns both our maker and taker fills for the market, and `extract_fills` then narrows to the specific `asset_id` client-side. The reconstruction itself replays our buys AND sells for the asset in time order, nets sells against buys FIFO, and the **lots that remain are the current position** — their weighted average is the cost. Critically, the reconstructed remaining size must match the Data API position `size` (tolerance `max(1, 0.01·size)`); if it doesn't (CLOB `get_trades` lagging behind the Data API position, or an externally-built/transferred position), the cost is treated as **unknown → skip**. This replaced an earlier "newest-to-oldest accumulate buys until size is covered" rule that ignored sells: when a recent buy fill hadn't yet propagated to `get_trades`, that rule fell back to an already-sold older buy and priced the sell below true cost, dumping the position at a loss (real incident 2026-05-28). It is **never** the Data API `avgPrice` under any circumstance (it glitches on freshly opened positions, causing undersell; the user banned it outright as a cost source); the Data API position is used only for `size`. **No avgPrice fallback exists:** if the cost can't be reconstructed (no fills, or reconstructed size ≠ position size), the exit *skips* that position (places/touches nothing) and emits a prominent `⚠️跳过·裸奔` warning status row so the unprotected position is visible — we never act on an uncertain cost. The skip self-heals: once `get_trades` catches up, the reconstructed size matches and the sell is placed at/above the true cost on the next tick. The exit is a **three-tier decision** (`check_exit` → pure `plan_exit` in `engine/take_profit.py`; `theta_loss`/`theta_stop` in price units = ¢/100): **Tier A** (cost ≤ best_bid, in profit) rests one sell at the **best ask** (maker; or market-clears if `case_a_mode='market'`; or rests at `ceil_to_tick(cost)` if `case_a_mode='cost'`, a marketable break-even sell that immediately fills at the bid yet never below cost); **underwater** (cost > best_bid) it actively limits loss — **B0** (loss ≥ `theta_stop`) market-sells (FAK stop-loss), **B_sweep** (best_bid ≥ cost − `theta_loss`) places a FAK marketable-limit at `ceil_to_tick(cost − theta_loss)` (capped loss), else **B_park** rests at the best ask which **may be below cost** (it deliberately parks at a loss to wait for recovery — SP3 **removed** the old `max(ceil_to_tick(cost), best_bid + tick)` never-sell-below-cost guardrail; θ-based active loss-limiting replaced it). `plan_take_profit` keeps **exactly one** resting sell at the planned price, cancelling/replacing mismatches. This replaced the old per-fill sell, which split one position into many orders priced off divergent per-fill `maker_orders` data. If a sell/stop-loss is rejected by the CLOB (`OrderRejected`), `check_exit` emits a prominent `⚠️…失败·裸奔` status row instead of failing silently, so the now-unprotected position is visible (the order was already cancelled before the failed replace). Both the take-profit and stop-loss `actions.price_basis` reasons spell out the per-lot cost composition (time + price×share + trade_id, via `describe_cost_basis`) so every sell traces back to the exact buy trades it was costed from. Step 3 first re-checks the **bid-ask spread** on each resting buy (`engine/eligibility.py` `recheck_resting_buy`, computed from the live orderbook): if `(best_ask − best_bid)` is at/over `max_spread_cents` it cancels the buy (cancel-only, no cooldown, positions untouched); an undeterminable spread (book side missing) is kept. Surviving buys then go through `determine_order_price`; if the recomputed target price falls outside the configured 单价区间 `[min_price_cents, max_price_cents]` (endpoints inclusive, mirroring the scanner's price-band filter) the buy is cancelled cancel-only (`price_band_cancel`, no replace), otherwise it is replaced/cancelled if its price no longer matches the current tick. Both price bounds default to no-op (`0`/`100`) when the settings keys are absent.

**Polymarket access (`api/polymarket_api.py`)** wraps `py-clob-client-v2`. Each `PolymarketAPI` is one wallet. Default `signature_type=2` (POLY_GNOSIS_SAFE), which needs a `funder` address — the user's deposit wallet (the Polymarket Gnosis Safe that actually holds funds), **not** the signer EOA. The user only enters a private key: when `funder` is omitted, `PolymarketAPI` derives it from the signer EOA via `derive_deposit_address` (CREATE2 against the Polymarket Safe factory, using the official `py_builder_relayer_client`), and `api_add_wallet` stores that derived address in the `wallets.funder` column. This derivation is verified to reproduce real deposit addresses. Rewards endpoints are static methods (no auth needed); order placement needs L2 creds derived at construction.

## Critical behaviors to preserve

- **Stopping the engine stops stop-loss monitoring.** `stop_all`/`stop_wallet` cancel open buy orders but also kill the monitor thread, leaving existing positions unprotected — the user-facing messages already warn about this; keep the warnings.
- **Startup recovery** (`startup_recovery` → `init_watermark`) seeds each monitor's trade watermark from DB trade history AND **primes `_seen_fill_keys` with every fill currently on record** (`get_trades(maker_address=funder)`). The watermark (DB `created_at`, local time) is only a conservative lower bound vs the exchange `match_time` that `get_trades(after=)` filters on, so it intentionally re-fetches a recent window; the precise dedup is `(trade_id, order_id)`. That dedup set lives only in memory, so before priming it a restart re-processed already-handled fills — re-recording `cancel_remainder` and re-setting cooldown for markets whose position was long closed (real 2026-05-29 observation). Priming it means **only fills that occur after startup trigger `_handle_fill`**; pre-startup/offline fills are not re-handled by Step 1 (the position they created is still protected by the position-driven take-profit, independent of Step 1). It no longer cancels stale orders or reconciles DB positions.
- **Balance is re-read before every order placement** (not cached per batch) so concurrent fills don't cause overspend — see commit history; preserve this. `place_orders` also reads each wallet's balance up front and skips any market whose recorded `min_cost` exceeds it, before fetching the orderbook.
- **UMA resolution guard cancels buys in resolving markets.** Once someone proposes a resolution on UMA, the Gamma market's `umaResolutionStatus` flips from `None` to non-empty (`proposed`→`disputed`→`resolved`) **while `acceptingOrders` stays `True` and `closed` stays `False`** — so the existing `closed`/`acceptingOrders` signals miss this window and a resting buy could still fill into a market about to settle. `engine/resolution.py` `in_resolution(status)` (non-empty = in resolution) gates two independent points (mirroring the blacklist's multi-point pattern): the monitor's `check_resolution` (runs each `_tick`, right after `check_buy_orders`) cancels **all BUY orders** for any market we hold buys in whose status is non-empty; `place_orders` skips placing into such markets so the cancel doesn't churn against the placement loop (different threads). Status is batch-fetched via `PolymarketAPI.gamma_resolution_status(condition_ids)` (Gamma `/markets?condition_ids=`), which **fails open** (`{}` on any Gamma error → cancel/skip nothing) so a transient outage never mass-cancels. Positions and resting SELLs are untouched (`check_exit` still exits before settlement). Always-on, no config key.
- **The `orders`/`positions` SQLite tables are no longer the source of truth.** Order management, `/api/positions`, dashboard counts, and the monitor all read the live Polymarket API. The `trades` table only holds `stop_loss` records now — the monitor no longer writes buy/sell rows (per-fill `maker_orders` prices were unreliable). Buy "history" in the UI **is the live Data API position** (`avgPrice`/`size`): the history page's holdings table reads `/api/positions`, and sell/stop-loss actions are shown from the `actions` table ("卖单理由"). The monitor watermark (`init_watermark`) seeds from `max(created_at)` over both `trades` and `actions` so clearing `trades` does not reset it.
- Orders are placed lowest-`market_competitiveness` first (less competition = larger reward share).
- Default strategy/risk parameters live in `config.py` `DEFAULTS`; user overrides are stored per-key in the `settings` table and merged on read. Settings changes take effect on next engine start unless restarted.
